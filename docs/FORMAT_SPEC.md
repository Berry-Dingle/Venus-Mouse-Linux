# UtechSmart Venus file-format specification

Status: reverse-engineered, file-only prototype specification.

Evidence labels:

- **FC** — confirmed by controlled file comparison.
- **DA** — confirmed by static disassembly of the official native application.
- **INF** — inference supported by multiple observations.
- **UNK** — unresolved.

This document does not specify permission to access a mouse. The prototype
package contains no USB or HID-device code.

## Common INI representation

PFD, MSMACRO, and both forms of MSDB are ASCII Windows INI files, normally
using CRLF line endings. **FC**

The official applications use `WritePrivateProfileStringW`,
`WritePrivateProfileStructW`, and their read counterparts. **DA**

Unknown keys, section ordering, values, padding, and anomalous `Count` values
must be preserved when an existing file is parsed and re-encoded.

## WritePrivateProfileStruct values

A structure of `N` bytes is stored as `2 × (N + 1)` hexadecimal characters:

```text
hex(data[0:N]) || hex(sum(data) modulo 256)
```

The final encoded byte is an unsigned additive checksum generated by
`WritePrivateProfileStructW`. It is not part of the in-memory structure. **FC,
DA**

For button and macro structures:

- input data: 189 bytes;
- encoded value: 190 bytes / 380 hex characters;
- checksum offset: encoded byte 189.

For `DPIStageValue`:

- input data: 408 bytes;
- encoded value: 409 bytes / 818 hex characters;
- checksum offset: encoded byte 408.

All 14 complete controlled macro bodies and 253 available controlled PFD
button/DPI structures validate this rule. **FC**

### ButtonAssigned semantic sections

Observed section names are `ButtonAssigned_1` through `ButtonAssigned_20`.
Fields:

```ini
ButtonID=255
ButtonFunc=<integer>
LoopNumber=<integer>    ; factory files only; omitted by newer saved samples
KeyNumber=<integer>
MacroName=<string>
```

`ButtonFunc=100` selects a macro. `KeyNumber` is its macro slot and
`MacroName` is the name used in `MacroSet.MSDB` and the MSMACRO filename.
**FC, DA**

For every intact controlled profile, `KeyNumber` equals the matching
`MacroSet.MSDB` list index. **FC** List order is therefore strongly inferred
to assign slots, but editor behavior after reordering/deleting entries has not
been tested. **INF**

The 189-byte button structure stored in the group section remained identical
between the ordinary-keyboard-1 baseline and every intact macro profile:

```text
data[0] = 0x1E
data[1:189] = 0
checksum = 0x1E
```

It preserves the prior ordinary keyboard assignment. It does not encode
function 100, macro name, macro slot, or loop mode. **FC**

Other observed `ButtonFunc` values exist, but a complete semantic enumeration
is **UNK**.

### DPIStageValue

`DPIStageValue` contains 408 data bytes and an additive checksum. **FC, DA**

Its beginning contains five 16-byte little-endian stage tuples: **FC**

```text
stage base = (stage - 1) * 16
base+0x00 uint32 enable
base+0x04 uint32 X sensor step
base+0x08 uint32 Y sensor step
base+0x0C uint32 flag (meaning unresolved)
```

The official UI has one slider per stage and every controlled save writes the
same raw step to X and Y. Asymmetric values may nevertheless be represented
by the file and are preserved, warned about, and never silently normalized.
The final tuple `flag` remains **UNK**.

#### DPI-stage enable state

Five controlled saves confirm that the first uint32 of each tuple is its
enable field: `1` is enabled and `0` is disabled. **FC** Disabling one stage
changes only that dword within the tuple; its X, Y, and trailing flag remain
unchanged. The other four tuples are unchanged.

| Stage | Enable | X | Y | Flag |
|---:|---:|---:|---:|---:|
| 1 | 0 | 4 | 8 | 12 |
| 2 | 16 | 20 | 24 | 28 |
| 3 | 32 | 36 | 40 | 44 |
| 4 | 48 | 52 | 56 | 60 |
| 5 | 64 | 68 | 72 | 76 |

The API exposes `dpi_stage_enabled_raw(stage)`,
`dpi_stage_enabled(stage)`, and
`set_dpi_stage_enabled(stage, enabled)`. The setter changes only the chosen
enable dword and additive checksum; it deliberately does not change the
selected-stage field. Unknown uint32 values are preserved and decode to
`None`, with a validation warning.

Every controlled file retains GROUP `DPI=1` (stage 2), including the file
where stage 2 is disabled. The user's direct UI observation was that disabling
a stage visibly selected the first enabled stage—stage 2 after disabling
stage 1, otherwise stage 1—but that UI fallback is not serialized in these
PFDs. **FC for saved bytes; UO for UI behavior** An editor-policy helper is
not provided because applying that policy would not reproduce the files.

`DPIStageNum` remains 5 even when any one stage, including stage 5, is
disabled. It is neither enabled count nor highest enabled stage. Fixed or
configured stage capacity is the best current interpretation. **FC, INF**

The raw format can represent all stages disabled or a disabled selected
stage. Whether an all-disabled profile can be applied is unresolved, so these
states are preserved with warnings rather than rejected or repaired.

#### DPI sensor-step conversion

Controlled files and two independent native-code paths in `ldcfg.exe`
establish the complete conversion for raw steps 1..106: **FC, DA**

```text
raw 1..61:    DPI = (raw + 1) * 100
raw 62..92:   DPI = (raw - 30) * 200
raw 93..105:  DPI = (raw - 51) * 300
raw 106:      DPI = 16400  (explicit special case)
```

Thus the legal editor domain is 200..6200 by 100, 6400..12400 by 200,
12600..16200 by 300, then 16400. This is piecewise-linear and quantized;
there is no evidence of a lookup table. Raw zero and values above 106 are
preserved as unknown rather than coerced.

The packed X/Y dword offsets are listed in the complete tuple table above.

For stage 1, the complete eight-character hexadecimal X and Y dwords occupy
raw PFD offsets 375..382 and 383..390 respectively. The controlled mapping is:

| DPI | Raw X | Raw Y | LE dword |
|---:|---:|---:|---|
| 200 | 1 | 1 | `01 00 00 00` |
| 400 | 3 | 3 | `03 00 00 00` |
| 800 | 7 | 7 | `07 00 00 00` |
| 1600 | 15 | 15 | `0F 00 00 00` |
| 3200 | 31 | 31 | `1F 00 00 00` |
| 6400 | 62 | 62 | `3E 00 00 00` |
| 12000 | 90 | 90 | `5A 00 00 00` |
| 16400 | 106 | 106 | `6A 00 00 00` |

The controlled `NM33_DPI1_12000.pfd` sample has X/Y raw value 90, and the
disassembled conversion displays 12000. **FC, DA**

#### Official-editor no-op resave normalization

Saving `NM00_Base.pfd` under a new name without changing any setting modifies
only `DPIStageValue.data[298:301]`: **FC**

```text
data offsets 298..300: 00 00 00 -> 0C 48 7F
outer checksum:         F2 -> C5
```

At raw PFD offsets, the actual changed characters are 964..968
(`00000 -> C487F`) and 1183..1184 (`F2 -> C5`). The complete encoded
three-byte span at offsets 963..968 changes `000000 -> 0C487F`; its first
character happens to remain `0`.

All other INI fields, all understood semantic settings, all button blobs and
sections, and all other 405 DPI payload bytes are identical. The no-op save
formally establishes this as editor-generated save normalization rather than
polling, brightness, palette-colour, or breathing-speed encoding. **FC**

The checksum change has no independent meaning: `0C + 48 + 7F = D3`, and
`(F2 + D3) mod 256 = C5`. It is exactly the additive checksum required by the
three changed payload bytes. **FC**

Observed saved batches have these values:

| Batch | `data[298:301]` | Checksum |
|---|---|---:|
| polling | `0C 48 BD` | `03` |
| brightness | `0C 48 18` | `5E` |
| palette colour | `0C 48 C9` | `0F` |
| breathing speed | `0C 48 7F` | `C5` |
| no-op resave | `0C 48 7F` | `C5` |

The first two bytes are stable in every observed editor save and the third is
stable within a controlled batch, but it varies between batches. The no-op
file matches the immediately preceding breathing batch. The evidence supports
a session/batch-volatile or cached editor value; it does not establish whether
repeated saves within one session always preserve it. **FC, INF**

As an arbitrary little-endian 24-bit number, `0C 48 7F` is `0x7F480C`
(8,341,516), while its first two bytes alone are `0x480C` (18,444). Neither
field boundary nor numeric interpretation is supported by code or samples.
The bytes lie in the otherwise-zero trailing/reserved DPI region. They are not
tied to any known current-stage or DPI-slider field because those known values
and every semantic setting remain unchanged, but a relationship to unknown
cached DPI UI state cannot yet be excluded. **UNK**

#### Selected/current DPI stage (`DPI`)

The semantic GROUP field `DPI` stores the selected stage as a zero-based
integer. It is not a bit mask and is not duplicated in the packed structure:
**FC**

| Stored `DPI` | Exposed stage | Controlled DPI value |
|---:|---:|---:|
| `0` | 1 | 1000 DPI |
| `1` | 2 | 2000 DPI |
| `2` | 3 | 4000 DPI |
| `3` | 4 | 8200 DPI |
| `4` | 5 | 16400 DPI |

The one-character decimal value begins at zero-based raw PFD offset 303, so
stages 1..5 use ASCII bytes `30`, `31`, `32`, `33`, and `34`. The setter
changes only this field.

The API exposes `selected_dpi_stage_raw`, `selected_dpi_stage`, and
`set_selected_dpi_stage(DpiStage.STAGE_4)`. Unknown raw integers remain
byte-exact and decode to `None`; setter requests outside one-based stages 1..5
are rejected.

All five controlled files have identical `DPIStageValue` payloads. Their first
five 16-byte little-endian tuples remain: **FC**

```text
(enable=1, X=9,   Y=9,   flag=1)
(enable=1, X=19,  Y=19,  flag=1)
(enable=1, X=39,  Y=39,  flag=1)
(enable=1, X=71,  Y=71,  flag=1)
(enable=1, X=106, Y=106, flag=1)
```

These unchanged raw sensor steps correspond to the controlled 1000, 2000,
4000, 8200, and 16400 DPI stages under the confirmed conversion above.
`DPIStageNum=5`, `DPICurrentX=14`, and `DPICurrentY=14` also remain constant
and do not duplicate selection state.

All five files contain identical no-op-resave bytes `0C 48 7F` at DPI data
offsets 298..300 with checksum `C5`. They do not vary with selection. The
setter preserves whichever tail was parsed and does not generate editor
normalization. **FC**

The file API exposes `dpi_stage_value(stage)`, `dpi_stage_value_raw(stage)`,
`dpi_stage_dpi(stage)`, and `set_dpi_stage_dpi(stage, dpi)`. The setter
changes only the selected tuple's X/Y dwords and the required outer additive
checksum. It preserves enable/flag words, selection, other stages, and the
opaque tail.

`DPICurrentX=14` and `DPICurrentY=14` remain constant in all controlled
DPI-value and selected-stage samples. They are neither the selected stage's
raw value nor a duplicate of the changed stage-1 value. Their semantics
remain **UNK**.

Related unresolved profile fields:

- `ANGLE`, `LIFT`, `OFA`, acceleration, and sensitivity device encodings;
- meanings of all non-macro button functions.

### Acceleration

`Acceleration` is a standalone decimal integer in the GROUP section. **FC**
It is not stored in `DPIStageValue`, a button blob, or any second semantic
field. Its value begins at zero-based raw PFD offset 133 for the controlled
one-digit values.

| Sample | Stored value |
|---|---:|
| clean baseline | 1 |
| fully left/minimum | 1 |
| approximate visual midpoint | 2 |
| fully right/maximum | 4 |

The controlled endpoints establish an editor range of 1..4. The file stores
an integer level, not a percentage or literal acceleration coefficient.
Native-code references at `ldcfg.exe` 0x42DC05 and 0x42E51C serialize the
dedicated integer member under the `Acceleration` key, separately from
`MouseSpeedX/Y`, wheel, and double-click fields. **FC, DA** No conversion or
duplicate packed representation was found.

The integer increment is 1. Values 1, 2, and 4 are directly confirmed by
official files; value 3 is the only remaining intermediate integer and is
supported by the range model, but lacks a dedicated controlled fixture.
**FC, INF**

The API exposes `acceleration_raw`, `acceleration`, and
`set_acceleration(value)`. Unknown decimal integers remain lossless and decode
to `None`. The setter accepts 1..4 and changes only the `Acceleration` text.

The physical interpretation remains unresolved: this is an editor/device
acceleration level, not demonstrated to be a percentage, Windows system
pointer-acceleration setting, or sensor register value. **UNK**

### Pointer speed (`MouseSensitivity`)

The General-tab Pointer Speed slider is stored as the standalone GROUP
`MouseSensitivity` decimal integer. **FC**

| Sample | Stored value |
|---|---:|
| fully left/minimum | 1 |
| clean baseline | 10 |
| approximate visual midpoint | 10 |
| fully right/maximum | 20 |

The value begins at raw PFD offset 70. The minimum file is one byte shorter
because `10` becomes `1`; this is normal variable-length INI text, not
truncation. The editor range is 1..20 with integer increment 1. Values 1, 10,
and 20 are directly sampled; intervening integers are the discrete positions
implied by this endpoint-controlled integer slider. **FC, INF**

`MouseSpeedX=10`, `MouseSpeedY=10`, and `XYSensitivityEnabled=0` remain
unchanged. They are not duplicated pointer-speed state. Native references at
`ldcfg.exe` 0x42DB4B and 0x42E462 serialize `MouseSensitivity` as its own
integer member. **DA** No packed copy or conversion was found.

Although 1..20 resembles the Windows system pointer-speed domain, identical
runtime semantics are not proven. **UNK**

The API exposes `pointer_speed_raw`, `pointer_speed`, and
`set_pointer_speed(value)`. Unknown integers remain lossless and decode to
`None`; the setter accepts 1..20 and changes only `MouseSensitivity`.

### Scroll speed (`WheelScrollLines`)

The General-tab Scroll Speed slider is stored as GROUP `WheelScrollLines`, a
variable-length decimal integer beginning at raw PFD offset 50. **FC**

| Sample | Stored value |
|---|---:|
| clean baseline | 1 |
| fully left/minimum | 1 |
| approximate visual midpoint | 33 |
| fully right/maximum | 63 |

The controlled endpoints establish range 1..63 with integer increment 1.
Values 1, 33, and 63 are directly sampled; other integers are the intervening
discrete slider positions. **FC, INF** Native references at `ldcfg.exe`
0x42DB0D and 0x42E424 serialize the dedicated integer under
`WheelScrollLines`; no conversion or packed duplicate was found. **DA**

The field name describes a wheel-scroll-lines count, not a percentage.
Whether its runtime behavior exactly matches the Windows
`SPI_SETWHEELSCROLLLINES` setting is not established. **UNK**

The API exposes `scroll_speed_raw`, `scroll_speed`, and
`set_scroll_speed(value)`. Unknown integers remain lossless; the setter
accepts 1..63 and changes only `WheelScrollLines`.

### Double-click speed (`DoubleClickSpeed`)

The General-tab slider stores a decimal speed level in GROUP
`DoubleClickSpeed`, beginning at raw PFD offset 91. **FC**

| Sample | Level | Windows threshold |
|---|---:|---:|
| fully left/minimum | 1 | 830 ms |
| clean baseline | 5 | 550 ms |
| approximate visual midpoint | 5 | 550 ms |
| fully right/maximum | 10 | 200 ms |

Disassembly at 0x414EC7–0x414ED2 and independently
0x41526D–0x41527E computes and calls: **DA**

```text
SetDoubleClickTime(900 - level * 70)
```

The stored value is therefore an inverse discrete speed level, not
milliseconds or a percentage. Higher levels mean a shorter threshold and
faster required clicking. The complete legal level range is 1..10 by 1,
mapping to 830..200 ms in descending 70-ms increments.

No duplicate or packed field changes. The API exposes
`double_click_speed_raw`, `double_click_speed`, `double_click_time_ms`, and
`set_double_click_speed(level)`. Unknown raw levels remain lossless.

### PollingRate

Controlled files map the complete editor enumeration: **FC**

| Stored `PollingRate` | Real rate |
|---:|---:|
| `8` | 125 Hz |
| `4` | 250 Hz |
| `2` | 500 Hz |
| `1` | 1000 Hz |

The file API exposes `PollingRateHz` and:

```python
profile.polling_rate_raw
profile.polling_rate_hz
profile.set_polling_rate_hz(PollingRateHz.HZ_500)
```

An unknown stored integer is retained byte-for-byte and decodes to
`polling_rate_hz is None`; it is never coerced to a known rate. Setting a rate
accepts only 125, 250, 500, or 1000 Hz.

Direct comparison among all four polling files shows that `PollingRate` is the
only rate-dependent field. No button structure, macro field, report metadata,
or other semantic field changes between rates. **FC**

Relative to the older approved baseline, all four editor-resaved polling files
also share one identical, rate-independent `DPIStageValue` mutation:

```text
DPI data offset 298: 00 -> 0C
DPI data offset 299: 00 -> 48
DPI data offset 300: 00 -> BD
checksum: F2 -> 03
```

The 500 Hz test has stored enum `2`, identical to the baseline, yet still has
this DPI mutation. Since all four tests share it exactly, it is a common editor
resave/normalization artifact rather than polling-rate encoding. Its semantic
meaning remains **UNK**. The polling setter deliberately changes only the
`PollingRate` field.

Controlled files map the complete editor brightness enumeration: **FC**

| Stored `LedState1` | Editor level |
|---:|---|
| `0` | Off |
| `1` | Low |
| `2` | Medium |
| `3` | High |

The API exposes `brightness_raw`, `brightness`, and
`set_brightness(BrightnessLevel.HIGH)`. Unknown stored integers are retained
byte-for-byte and decode to `brightness is None`; the setter accepts only the
four levels above and changes only `LedState1`.

Pairwise comparison finds `LedState1` is the only brightness-dependent field.
`FlashState1=5`, `BreathState1=5`, `LedMode1=0`, `LedColor1=255`,

Relative to `NM00_Base.pfd`, all four share this brightness-independent

```text

checksum: F2 -> 5E
```

The Medium file has the baseline `LedState1=2` yet still has this mutation.
It is therefore not brightness encoding. **FC** Its meaning remains **UNK**
and the brightness setter does not reproduce it.

Controlled files map the complete editor enumeration: **FC**

| Stored `BreathState1` | Editor value |
|---:|---|

| `5` | Medium |
| `2` | High |

### LED mode (`LedMode1`)

Controlled files map the complete editor enumeration: **FC**

| Stored `LedMode1` | Editor mode |
|---:|---|
| `0` | Breathing |
| `1` | Full Brightness |
| `2` | Rainbow |
| `3` | Wave |

```text
DPI data[298:301]: 0C 48 7F
DPI checksum: C5
```

Against `NM00_Base.pfd`, the actual unrelated raw differences are offsets
964..968 (`00000 -> C487F`) and 1183..1184 (`F2 -> C5`). The Breathing sample
retains baseline `LedMode1=0` but still contains them, independently confirming
that the DPI tail is save normalization and not mode encoding. The setter

The three similarly worded controls are independent:

```text

Brightness Level High:          LedState1=3
Breathing Speed Full Brightness: BreathState1=0
```

In `NM17_ModeFull.pfd`, `LedMode1=1` while brightness remains Medium
(`LedState1=2`) and breathing speed remains Medium (`BreathState1=5`). **FC**

The parser exposes `flash_state_raw` separately so its exact underlying value
is not hidden, but it is deliberately excluded from `set_led_mode()`. Unknown
`LedMode1` integers decode to `None`, produce a validation warning, and remain
lossless. Since the official representation is a single enum, there are no
multi-field official/malformed mode combinations to normalize; an unknown
enum is the unsupported raw state.

### Palette colour (`LedColor1`)

`LedColor1` is a decimal unsigned 24-bit Windows `COLORREF`: **FC, DA**

```text
integer bits: 0x00BBGGRR
little-endian dword bytes: RR GG BB 00
```

Thus the high byte is unused/zero, the low integer byte is red, then green,
then blue. The decimal INI text itself has no byte order; the byte ordering
above applies when the integer is packed in memory or a binary structure.

checksum `F2 -> 0F`. Its meaning is **UNK**; the setter does not reproduce it.

#### Arbitrary RGB and official-picker quirk

The custom-picker sample entered as RGB `#123456` stores:

```text
LedColor1 decimal:       1193046
stored integer:          0x00123456
little-endian dword:     56 34 12 00
COLORREF-decoded RGB:    #563412 = (86, 52, 18)
```

This is not the expected COLORREF for RGB `#123456`, which is
`0x00563412` (decimal 5,649,426; bytes `12 34 56 00`). The official picker
preserves the typed six hexadecimal digits as an integer without performing
the RGB-to-COLORREF red/blue swap. **FC** No additional field changes.

The semantic API does not reproduce this quirk silently:

```python
profile.led_color_hex
profile.led_color_raw_hex
profile.set_led_color_rgb(r, g, b)
profile.set_led_color_hex("#RRGGBB")  # leading # optional
```

RGB setters encode exact `0x00BBGGRR`; channels must be integers 0..255.
Hex parsing accepts exactly `#RRGGBB` or `RRGGBB`. There is no alpha byte:
the upper byte is zero. Arbitrary non-palette values and the official
quirked sample remain lossless. **FC**

## MSMACRO

An MSMACRO has one `[Setting]` section:

```ini
MacroFilePath=<path ending .MSMACRO>
LoopTime=<integer>
DefDelayTime=<milliseconds>
LoopType=<0..3>
DelayType=<0..2>
Count=<0..63>
MacroSetting_0=<189 data bytes plus checksum, represented as hex>
```

Field order varies between samples and is not semantic. **FC**

`MacroSetting_0` is 63 three-byte record slots. `Count` selects the prefix
copied by `hid.exe` as `Count × 3` bytes. Remaining records are normally zero
padding. **FC, DA**

### Count anomaly

`12_MouseLeftClick` stores `Count=8`, but only records 0 and 1 are non-zero;
records 2 through 7 are zero triples. MSDB and MSMACRO copies agree. A parser
must preserve this. A validator should warn rather than silently changing
Count. **FC**

## Per-macro MSDB

A named standalone MSDB uses the same `[Setting]` schema and structure as an
MSMACRO. In every complete controlled pair, all settings and action bytes are
identical; only `MacroFilePath` and its extension differ. **FC**

Directory layout indicates:

- `.MSDB` is an exported or standalone macro representation;
- `MacroDB/<name>.MSMACRO` is the active editor database copy.

This lifecycle interpretation is **INF**; the exact save/import workflow is
not fully traced.

Some supplied MSMACRO files omit `MacroSetting_0` while their MSDB counterpart
is complete. This is official-editor output that must remain losslessly
parseable but fails complete-macro validation. **FC**

## MacroSet.MSDB

The active macro list is:

```ini
[MACRO_LIST]
0=<name or empty>
...
14=<name or empty>
[Setting]
Device=1
FirstOpen=1
```

There are exactly 15 slots, indexed 0 through 14. Empty slots remain explicit.
Names map to `MacroDB/<name>.MSMACRO`. **FC**

Maximum macros: 15. **FC**

Whether deleted names can remain as residue, how gaps are reused, and how the
editor rewrites existing PFD assignments after reordering are **UNK**.

## Three-byte action records

Every action record is:

```text
byte 0: family in bits 0..6; state/down flag in bit 7
byte 1: family-specific value
byte 2: family-specific value
```

Record capacity is 63. `ldcfg.exe` advances by 3 and stops at `0x3F`. **DA**

### Keyboard

```text
84 <HID keyboard usage> 00    key down
04 <HID keyboard usage> 00    key up
```

Confirmed usages include:

- `08` E
- `14` Q
- `15` R
- `17` T
- `1A` W
- `1E..22` digits 1 through 5
- `E0` Left Control

The editor masks byte 0 with `0x7F`, selects family 4, uses byte 1 as the
keyboard usage, and branches on bit `0x80`. **FC, DA**

Held modifiers and overlaps are represented by ordinary down/up state:
modifier down, other key pairs, modifier up. **FC**

### Mouse buttons

```text
81 <button mask> 00    button down
01 <button mask> 00    button up
```

Masks:

- `01` left;
- `02` right;
- `04` middle.

Left/right are confirmed by controlled files. Middle is confirmed by the
editor's parser disassembly but lacks a file sample. **FC, DA**

The values are masks, not ordinal button numbers: middle is `04`, not `03`.
**DA**

An inserted click is two records, explicit down then up. Mixed keyboard/mouse
records are directly interleaved. **FC**

Mouse-wheel records are not supported by this editor version and are outside
scope.

### Action delay

```text
06 <low> <high>
```

An **Action delay** is an ordinary macro action record. Its value is a
little-endian unsigned 16-bit integer multiplied by 10 ms.
**FC, DA**

Examples:

- `06 01 00` = 10 ms;
- `06 19 00` = 250 ms;
- `06 F4 01` = 5000 ms.

Representable binary range: 0 through 655,350 ms in one record, in 10 ms
increments. Values not divisible by 10 ms are not exactly representable and
the prototype rejects them rather than silently rounding. **DA/prototype
policy**

An individual action-list delay row can store and reload 5000 ms, encoded as
`06 F4 01`. **FC plus user-verified editor reopen** The meaning of raw zero
remains **UNK**.

Long delays are not split when one record suffices. **FC**

### Zero and unknown records

`00 00 00` is padding/empty. It may occur inside Count because of the
mouse-click anomaly. **FC**

All unrecognized triples must be retained byte-for-byte and surfaced by
validation. Families 2 and 3 are recognized by portions of editor code but
not represented in the controlled files; their semantics are **UNK**. **DA**

## Default inserted delay and delay-mode metadata

**Default inserted delay** and **Action delay** are separate concepts:

- `DefDelayTime` is editor metadata used when `DelayType=1`/INSERT DEFAULT
  DELAY inserts delays;
- an Action delay is a type-6 record already present in `MacroSetting_0`.

The Windows default-delay input is limited to three decimal digits. The
practical accepted metadata range is 0–999 ms. The prototype validates that
range. A default value need not be divisible by 10 because it is preserved as
metadata; converting it into an Action delay must use an explicit caller/UI
policy. The core never derives or rewrites one from the other automatically.
**Controlled UI behavior/prototype policy**

Controlled mapping:

- `DelayType=0`: RECORD DELAYS BETWEEN ACTION;
- `DelayType=1`: INSERT DEFAULT DELAY;
- `DelayType=2`: no automatic delay.

**FC**

Recorded delays are quantized to 10 ms and expanded into type-6 records.
Default inserted delay 250 becomes raw value 25 in each inserted record.
Therefore
`DefDelayTime` is an editor insertion default, not runtime-only metadata.
**FC**

No-automatic-delay output may still contain editor-minimum or existing
explicit delay records. The controlled “NoDelay” file contains three 10 ms
records, while another type-2 file retains an explicit 5000 ms record. **FC**

The recreated `10_Keys12_NoDelayR.MSMACRO` independently preserves the same
three 10 ms records with `DelayType=2`, `Count=7`, and a valid checksum. **FC**

## Loop metadata

Mapping:

- `LoopType=0`: fixed total execution count; `LoopTime=N`;
- `LoopType=1`: repeat while the assigning mouse button remains held;
- `LoopType=2`: run once;
- `LoopType=3`: toggle continuous repeat until another press.

**FC, DA**

`hid.exe` button-packet construction:

- type 0: sends unflagged slot and `LoopTime` as a 16-bit count;
- type 1: ORs `0x80` into the slot byte;
- type 2: forces transmitted count to `0x0001`;
- type 3: ORs `0x40` into the slot byte and forces count `0xFFFF`.

**DA**

No one is added to fixed `LoopTime`. A value of 3 means three total
executions. Actions are not duplicated for looping. **FC, DA**

Loop behavior is compiled into the macro button assignment/control packet,
not the report-4 action body or the unchanged PFD button blob. **DA, FC**

## Slot addresses and report 4

Macro slot address:

```text
address(slot) = 0x0478 + slot × 0x00C8
slot range = 0..14
```

Examples:

- slot 0: `0x0478`;
- slot 1: `0x0540`;
- slot 14: `0x0F68`.

**DA, FC**

The macro body transfer begins:

```text
04 F3 <address-low> <address-high> C8 00 00 00 <Count × 3 bytes> ...
```

Report length is 1024 bytes and device slot stride is 200 bytes. **DA**

The INI checksum and unused 189-byte padding are not copied as action data.
**DA**

The exact semantics of every remaining byte in the 200-byte device slot,
device acknowledgments, ordering/timing requirements, commit behavior, and
readback verification remain **UNK**. This prototype does not implement that
transport.

## Validation requirements

A conforming strict validator should:

- parse without normalizing unknown keys or ordering;
- require complete macro fields when validating a macro;
- require 189 macro/button data bytes and 408 DPI data bytes;
- verify additive checksums;
- enforce Count range 0..63;
- warn for zero records inside Count and data after Count;
- preserve and warn for unknown records;
- track keyboard/mouse held states and report missing releases;
- validate PFD macro slot range 0..14;
- compare PFD `KeyNumber`/`MacroName` with `MacroSet.MSDB`;
- check for the corresponding MSMACRO file when context is available;
- report truncated PFD sections rather than repairing them.
